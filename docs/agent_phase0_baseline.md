## Existing boundaries to reuse

- Runtime application: `api/app` (FastAPI/SQLAlchemy) and `web` (React/Vite). Reuse `current_user`, `member_trip`, database sessions, route helpers and `api/app/services.py` adapters.
- Recommendation computation: `services/recommender/main.py` and `src/ourney_travelsync/recommenders`. The API defaults to `individual_method='tfidf'`; the direct legacy service contract defaults to binary when that field is omitted. Preserve both contracts, declared score scales, seeded tie behavior, GFAR settings and comparison methods.
- Compose connects recommendation calls to the real service on port 8002. Optimization, availability and agent calls target `services/mocks` on port 8001. The availability service contains real, limited SQL-backed checking logic despite being hosted under mocks; its placement is not proof that every returned value is fabricated. The planner is a greedy stand-in and the agent is a keyword stub.
- Existing identity types remain: string trip/user IDs, integer recommendation Run/itinerary IDs, string dataset/schema versions and opaque POI IDs such as source-prefixed strings. Do not migrate these to the proposal's generic UUID examples. Use the application's `/trips/{trip_id}` namespace rather than creating a parallel group domain.
- `src/ourney_travelsync/db` and `database/schema.sql` form a separate repository/schema boundary with overlapping, incompatible table names. They are not the web API's persistence layer. Do not install that schema over the application database. Any later extension storage must be additive and application-compatible.
- Reuse existing preferences, taste surveys, exclusions and Run request/response data. Read-only assistance does not need a new universal constraint/versioning model, full-matrix persistence or a solver rewrite.

## What is a difference and what needs a fix

- TF-IDF versus the old weighted Feature formula, 1-5 binary scores, seeded ties, GFAR depth and single-member ordering are **documented current behavior to preserve**. Earlier fixture comparisons demonstrate different policies; they are not failures against the revised authority. The legacy voting rule is also separate existing behavior.
- The reproduced break-time availability=true result is a **confirmed false positive relative to the checker's own whole-visit availability meaning**. Address or guard it when promising time-window feasibility; it does not prevent truthful read-only assistance today.
- Inferred indoor flags and rough travel times are **estimates/inferences with limited evidence**. Keep their current application meaning; ensure the agent labels them honestly. Do not assume that changing the boolean or displaying a precise number verifies the fact.
- A real evaluator, independent final validation, proposal approval and safe application are **missing extension capabilities**. Their absence does not justify replacing the recommender. Disable change tools until their safeguards exist.

## Small first milestone for the next response

**Revised Phase 1: authenticated read-only context and evidence tools.** Deliver a reviewable backend boundary ready for the single agent. It is not yet a conversational AI feature.

Scope:

1. Add a small module inside `api/app` with strict Pydantic input/output schemas and three allowlisted functions: `get_trip_context`, `get_poi_information`, and `get_recommendation_evidence`. Reuse existing database sessions, lookup/formatting helpers and stored recommendation results. Do not recompute recommendations during a read.
2. Derive the actor from existing authentication and verify trip membership on each call. Check that any Run/itinerary belongs to that trip, pin POI lookup to the selected Run's dataset when a Run is supplied, and reject malformed/oversized inputs. Keep opaque POI IDs and existing numeric Run/itinerary IDs.
3. Build a bounded evidence projection. Exclude other members' raw ratings, taste answers/keywords, personal exclusion details, email addresses, full Run requests and the full POI corpus. Return stored values with source references and available timestamps. Distinguish unknown, estimated and rule-inferred facts from verified ones; do not invent verification timestamps or causal score contributions.
4. Expose one feature-flagged authenticated inspection endpoint, proposed as `GET /trips/{trip_id}/agent/context`, which returns this bounded bundle with an additive `agent.v1` schema. Existing trip/recommendation/POI response schemas remain unchanged. This is a read endpoint for review, not the proposal's future job/request endpoint. No LLM, chat storage, job queue, proposal tables or frontend work is required for this milestone.
5. Add focused tests for authorization, cross-trip IDs, exact stored score/rank evidence, missing recommendations, bounded POI lookup, privacy, inferred/unknown facts and absence of writes. Keep the flag off by default and verify the existing application still behaves the same.

Acceptance: a member can inspect a bounded, accurate bundle for their trip; nonmembers/forged references are rejected; no private raw preferences reach it; source/estimate labels are honest; database contents are unchanged by reads; and existing TF-IDF/GFAR behavior remains unchanged. Actual LLM invocation, proposal evaluation and itinerary application remain unavailable.

## Subsequent capability gates

- **Read-only conversation:** build on the three tools with one configurable LLM, strict supported read intents, clarification, explicit `@TravelSync`/quick-action triggers, request/job state, limits and feature flag. Consult current official provider documentation during implementation. Adapt request contracts to trip IDs and optional existing Run/plan references; do not invent a committed `base_revision` before revisions exist. Jobs become durable when introduced. Recovery can begin with authenticated GET before WebSocket delivery.
- **Explicit recommendation recomputation, if added:** call the current recommendation API/service through a write/computation-specific action. It creates a new Run; it is not a silent side effect of `get_recommendation_evidence`. It must not replace a selected/confirmed itinerary.
- **Evaluated itinerary proposals:** implement only the data, constraint and evaluation additions needed for the promised changes, through existing service boundaries. Evaluate without invoking the destructive generation route. Preserve locks and unchanged activities; validate affected connections and the full itinerary for applicable time/budget/duplicates/movement/return constraints. Missing inputs produce typed unknown/unsupported/clarification states, not a validated plan. CP-SAT is not present in the production path; no solver implementation or broad optimization rewrite is selected in Phase 0, and none is a prerequisite for read-only tools.
- **Approval and application:** add application-compatible proposal/revision/audit/outbox records, frozen unanimous policy and expiry, stale-input checks, final independent validation and atomic idempotent application before enabling confirmed changes. Adapt identifiers and existing version references rather than replacing schemas. The LLM never commits. Keep system ADMIN actions separate from trip OWNER authority; no POI approval functionality is needed for the first milestone.
- **Interface and delivery:** add proposal/vote/recovery UI once backend contracts work, then run real service/browser/fault/concurrency checks. Report measured model/API latency, tokens and costs separately. Old SRS performance targets are historical reference goals, not newly imposed acceptance gates; agree capability-specific measurement conditions before claiming performance. Functional passes and internal utility do not demonstrate user satisfaction.
